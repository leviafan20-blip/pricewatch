# Архитектурные решения PriceWatch

## Принятый ориентир

Модульный Django-монолит: серверные шаблоны, Bootstrap, PostgreSQL, позднее
Celery/Redis и HTTPX/BeautifulSoup. Playwright подключается только для выбранных
динамических сайтов. Прикладная логика остаётся на Python; JavaScript нужен
только для отдельных интерактивных элементов.

Решения владельца проекта:

- Начать с 2–3 поддерживаемых сайтов и собственного демонстрационного магазина.
- Публичную регистрацию не создавать.
- Уведомления первой версии показывать внутри приложения.
- Изменения содержимого отслеживать по выбранному CSS-блоку.
- Следующие возможности добавлять только при переходе к соответствующему этапу.

## Этап 1

`accounts` содержит минимальный `User(AbstractUser)`. Собственная модель создана
с первой миграции: последующая смена таблицы пользователей была бы сложнее.
Проверки паролей, сессии, разрешения и формы администрирования предоставлены Django.

`core` содержит кабинет с обязательной авторизацией и две проверки состояния:
`/health/live/` не обращается к БД, `/health/ready/` выполняет `SELECT 1`.
Ошибки подключения не раскрываются в HTTP-ответе.

Внешний ввод обрабатывается Django Forms. Успешный вход создаёт серверную сессию
в PostgreSQL; браузер получает session cookie. Изменяющие запросы защищены CSRF.
Выйти можно только POST-запросом. Внешний URL в `next` не принимается штатным LoginView.

Локальное окружение состоит из PostgreSQL, одноразового запуска миграций и Django.
База хранится в именованном volume. Веб-процесс работает в контейнере от отдельного
непривилегированного пользователя. Миграции создаются разработчиком и хранятся
в проекте; автоматически при старте выполняется только их применение.

## Этап 2

`monitoring.scraping` разделяет проверку адреса, безопасное соединение,
правила robots, общие ограничения домена, загрузку, нормализацию и извлечение.
Бизнес-моделей товаров или наблюдений пока нет. Единственная служебная таблица
`SiteAccessState` координирует частоту и исключает перекрывающиеся запросы разных
процессов. Сеть выполняется вне транзакции; право на запрос имеет ограниченный срок.

HTTPX использует небольшой адаптер публичного HTTPcore NetworkBackend API.
Он нужен для фактического подключения к проверенному IP с исходным Host/TLS SNI
и оставшимся общим тайм-аутом при каждом чтении сокета. Приватные API HTTPX
и подмена глобального DNS resolver в приложении не используются.

`extract_product` — обычная Python-функция без Django и сети. Команда
`parse_product` позволяет запускать её на локальном HTML. Работу с URL объединяет
`apps.monitoring.services.inspect_url`. Список разрешённых сайтов по умолчанию пуст.

## Этап 3

Ручной мониторинг использует `Monitor` с владельцем и настройками,
`CheckRun` с неизменяемой копией входных данных и `Observation` для успешного
результата. Ошибка проверки не изменяет прошлые наблюдения. Пара Monitor →
активный CheckRun защищена частичным уникальным индексом, а результат →
CheckRun — связью один-к-одному.

Короткие транзакции блокируют строку Monitor при изменении состояния.
Отдельная PostgreSQL advisory lock привязана к сессии worker и удерживается
во время сети без открытой транзакции. Повторная доставка либо пропускается,
либо продолжает ту же попытку после гибели предыдущего worker.

Celery/Redis добавлены для ручных задач. Результаты остаются в PostgreSQL,
Celery result backend и beat не подключены. Между фиксацией попытки и отправкой
не нужна распределённая транзакция: повторная отправка того же UUID безопасна
и восстанавливает пропущенную публикацию. Настройки TLS/SSRF/robots этапа 2
не ослабляются. Подробности и эксплуатация: `components/monitoring.md`.

## Этап 4

Один Celery Beat раз в минуту вызывает диспетчер. Расписания Monitor
хранятся в PostgreSQL; отдельной таблицы стороннего scheduler нет.
`FOR UPDATE SKIP LOCKED` разделяет работу конкурентных диспетчеров.
Они создают только одну актуальную попытку и сдвигают следующий срок
от текущего времени, не воспроизводя все пропущенные интервалы.

CheckRun хранит исходный плановый слот и ограниченную по времени резервацию
доставки. После сбоя публикация восстанавливается тем же UUID, максимум
три автоматические отправки. Сеть по-прежнему выполняет прежний worker
с advisory lock, общими доменными лимитами и `inspect_url()`.
Пауза/архив проверяются и диспетчером, и worker перед сетью.

Celery и PostgreSQL используют UTC, шаблоны — текущий часовой пояс Django.
Beat хранит состояние таймера в отдельном volume, PID — во временной памяти.
Данные пользователя и сроки не зависят от файла Beat. Устройство, гарантии
доставки и диагностика: `components/scheduling.md`.

## Этап 5

История и аналитика читают существующие Observation, технический журнал —
CheckRun. Django фильтрует данные владельца, период и одну валюту; PostgreSQL
считает numeric-агрегаты, Python использует Decimal. Сравнение ограничено
пятью товарами; SQL-запросы выполняются пакетно, без N+1.

Chart.js 4.5.1 подключён локально в Django Templates. Через json_script
передаются строки цен и UTC-время, JavaScript только рисует. Оконная выборка
ограничивает график 400 точками на товар, статистика остаётся полной.
Наблюдения и журнал имеют независимую пагинацию по 20 строк. Новых таблиц,
задач и копий истории нет. Подробности: `components/analytics.md`.

## Этап 6

Правило цены хранится у Monitor, email-разрешение — у User. Внутреннее событие
Notification создаётся в одной транзакции с Observation при успешном завершении
прежнего CheckRun. Ссылки на два наблюдения сохраняют цены без копирования.
OneToOne нового Observation исключает повтор события; Decimal-расчёт изменения
вынесен в `monitoring/money.py` и используется также аналитикой.

Notification содержит небольшую email-outbox. Beat резервирует до 20 pending
строк с SKIP LOCKED; публикация в Redis происходит после коммита. Отдельная
Celery-задача фиксирует sending до внешнего I/O и отправляет стандартным Django
backend. Повторные задачи не отправляют письмо повторно. Неопределённый исход
SMTP после начала отправки не повторяется автоматически; внутреннее событие
сохраняется. Локальный backend console, интеграционный — filebased.
Права, состояния, команды и компромиссы: `components/notifications.md`.

## Следующие этапы — ещё не реализованы

Далее появятся CSV/XLSX и мониторинг текстовых блоков.
Проверки выполнения уже отделены от успешных наблюдений.

До добавления новых компонентов отдельные приложения, таблицы, очереди и
абстракции для них не создаются. Общий каталог товаров разных магазинов,
микросервисы и полноценный внешний REST API пока не требуются.
