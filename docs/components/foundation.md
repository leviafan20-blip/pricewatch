# Этап 1: основа проекта

## За что отвечает компонент

Основа обеспечивает запуск Django с PostgreSQL, создание учётных записей
администратором, вход/выход, закрытый кабинет и воспроизводимые тесты.
Функциональность сбора цен ещё не подключена.

## Где находится реализация

| Файл / каталог | Назначение |
| --- | --- |
| `config/settings/` | Общая конфигурация, локальное окружение и тестовые настройки |
| `config/urls.py` | Подключение маршрутов приложения и admin |
| `apps/accounts/models.py` | Собственная модель пользователя на основе Django |
| `apps/accounts/forms.py` | Оформление формы входа и формы admin для своей модели |
| `apps/accounts/admin.py` | Регистрация модели в административной панели |
| `apps/accounts/urls.py` | Только вход и POST-выход; регистрации нет |
| `apps/accounts/migrations/0001_initial.py` | Исходная схема пользователей |
| `apps/core/views.py` | Защищённый кабинет и состояние приложения/БД |
| `templates/`, `static/` | Серверный интерфейс и локальный Bootstrap |
| `compose.yaml` | PostgreSQL → миграции → запуск Django |
| `tests/` | Поведенческие тесты доступа, admin и ошибок БД |

## Как проходят данные

1. Анонимный запрос кабинета перенаправляется на страницу входа с локальным `next`.
2. Браузер получает форму с CSRF-токеном и отправляет имя пользователя и пароль.
3. Django проверяет токен, учётные данные и активность пользователя.
4. При успехе Django создаёт сессию в БД и выдаёт session cookie.
5. Следующий запрос получает `request.user`; шаблон отображает кабинет.
6. POST-выход очищает сессию. GET-запрос выхода не меняет состояние.

Пароль хранится как хеш. Неверное имя и неверный пароль дают одно общее сообщение.
Значения пользователя в шаблонах экранируются. Своих механизмов проверки паролей
и сериализации сессий проект не вводит.

## Какие ошибки возможны

- **Не задан DJANGO_SECRET_KEY:** настройки локального приложения не загрузятся.
  Проверьте `.env` и способ передачи переменных; не публикуйте секрет в логах.
- **Docker не запущен:** `docker info` не показывает Server. Это возникает до
  запуска приложения; диагностируйте Docker Desktop отдельно.
- **PostgreSQL недоступен:** readiness возвращает 503, вход не сможет прочитать БД.
  Смотрите состояние `postgres`, затем `migrate` и логи `web`.
- **Пароль БД изменён только в .env:** уже существующий volume сохраняет старую
  учётную запись. Изменение переменной не меняет пароль внутри существующей БД.
- **Миграции не применились:** `web` не стартует при неуспехе `migrate`.
  Исправьте ошибку и повторно выполните миграции.
- **403 на форме:** CSRF-токен/Origin не совпадают. Используйте один адрес
  приложения; при изменении адреса или порта обновите разрешённые origins.
- **DisallowedHost:** добавьте используемое имя в `DJANGO_ALLOWED_HOSTS`.
- **Вход отклонён:** проверьте имя, пароль и `is_active` через admin/management command.

## Как проверить и отладить

Начните с `docker compose ps -a`, затем `docker compose logs --tail=100 web migrate postgres`.
Не публикуйте полный `.env` и вывод `docker compose config` с раскрытыми переменными.
Для проверки синтаксиса конфигурации используйте `docker compose config --quiet`.

`manage.py check` проверяет настройки; `makemigrations --check --dry-run` обнаруживает
забытые миграции. Pytest проверяет вход, безопасный `next`, выход, CSRF, admin,
неактивного пользователя, экранирование и деградацию readiness.

Локальный SQLite fallback полезен для быстрой проверки, но основная проверка
и CI используют PostgreSQL. Покрытие небольшого пользовательского кода не означает,
что проверены все сценарии инфраструктуры или будущего мониторинга.
