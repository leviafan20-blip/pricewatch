# Этап 5: история цен и аналитика

## Ответственность и файлы

Компонент читает существующие Observation; CheckRun остаётся журналом попыток.
Новых моделей, таблиц, миграций, задач и зависимостей Python нет.

| Файл | Назначение |
| --- | --- |

| `apps/monitoring/forms.py` | HistoryFilterForm: период, даты и валюта |
| `apps/monitoring/views.py`, `urls.py` | Проверка владельца, карточка и GET `/monitors/compare/` |

## Как обрабатываются данные

1. Django проверяет вход и получает Monitor с `owner=request.user`. Для
   сравнения проверяется каждый ID: чужой или отсутствующий возвращает 404;
   не более пяти ID. Из списка выбираются товары текущей страницы (20 строк).
2. HistoryFilterForm проверяет период 7/30/90/all, ISO-даты и валюту из истории
   выбранных товаров. Некорректный фильтр не заменяется полной историей.
   Если в истории несколько валют, требуется явно выбрать одну.
3. `history_window()` фиксирует верхнюю границу текущим временем. Периоды —
   последние 7/30/90 × 24 часа; даты уточняют их. «По дату» включительно:
   SQL использует начало следующего местного дня как исключающую границу.
   Для произвольного старого диапазона нужно выбрать «Всё время». Даты и
   подписи используют активную временную зону Django, хранение — UTC.
4. Observation выбираются через принадлежность CheckRun мониторингу. Только
   ненулевые (`price IS NOT NULL`, включая цену 0) цены выбранной валюты
   участвуют в Min/Max/Avg/Count PostgreSQL. AVG работает с numeric, Python
   получает Decimal. Средняя относится к наблюдениям, а не длительности цены.
5. Первое и последнее значения определяются по `(observed_at, pk)`. Изменение:
   `последняя − первая`; процент: `изменение / первая × Decimal(100)`.
   Decimal-контекст — 60 значащих цифр; при первой цене 0 процент не определён.
   Средняя и процент округляются до двух знаков только при отображении;
   реальные цены и абсолютное изменение отображаются без округления.
6. Все мониторинги сравнения обрабатываются пакетно: 5 SQL-запросов для
   небольшой истории, 9 при выборке большой истории, независимо от числа
   товаров. На график передаётся максимум 400 точек на товар, до 2000 всего.
   PostgreSQL вычисляет RowNumber внутри каждого товара; равномерная выборка
   сохраняет крайние наблюдения и первое/последнее/минимальное/максимальное
   валидные значения. Статистика всегда использует все строки периода.
7. Маленькая история содержит наблюдения без цены как JSON null: они
   разрывают линию. Для сокращённой истории линия отключается: выборка не
   должна маскировать пропущенные разрывы. Она может пропустить локальные
   колебания; глобальные минимум и максимум сохраняются. Ошибок CheckRun
   на графике нет; график не утверждает цену между измерениями.
8. `json_script` безопасно экранирует названия и передаёт цены строками.
   `price-history.js` преобразует их через Number только для координат.
   Tooltip использует исходную денежную строку. Горизонтальная линейная ось
   содержит UTC milliseconds, Intl форматирует даты в зоне Django. Адаптеры
   дат и дополнительные JS-библиотеки не нужны.
9. Наблюдения показываются отдельно, по 20 на страницу (`obs_page`);
   журнал попыток — независимо по 20 (`page`). GET-фильтры сохраняются.
   Журнал за всё время явно подписан и не зависит от ценовых фильтров.
   Запросы не изменяют историю, расписания и очередь.

Chart.js подключён обычным script tag согласно
[официальной документации](https://www.chartjs.org/docs/latest/getting-started/integration.html).
Использована [линейная ось](https://www.chartjs.org/docs/latest/axes/cartesian/linear.html)
с UTC-координатами, поэтому отдельный time adapter не требуется.
Готовая сборка хранится локально; CDN при открытии страницы не используется.
SHA256 `chart.umd.min.js`: `48444a82d4edcb5bec0f1965faacdde18d9c17db3063d042abada2f705c9f54a`.

## Ошибки и самостоятельная проверка

- Неверный период, даты или валюта: форма показывает ошибку, график и таблица
  не подменяются более широкими результатами.
- Нет общей валюты или у одного товара нет цен периода: сравнение объясняет
  причину и не строит несопоставимые ряды. Автоматической конвертации нет.
- Нет данных, одна цена, неизменная цена, возврат к первоначальной цене:
  отдельные сообщения. Наблюдения «нет в наличии, цена неизвестна» не равны 0.
- Ошибка загрузки JS/Chart.js: статистика и таблица остаются HTML. Сообщение
  об ошибке построения появляется под графиком, подробность — в console.
- На текущий момент у всех пользователей одна настроенная временная зона
  `Asia/Yekaterinburg`; персональные настройки зоны не добавлены.

Быстрая проверка без сайтов:

```powershell
docker compose -p pricewatch -f compose.yaml exec -T web python -m pytest tests/monitoring/test_analytics.py --ds=config.settings.test --reuse-db -q
```

Для воспроизводимой проверки в браузере после тестов (БД `test_pricewatch`
должна уже существовать; профиль интеграции не должен использоваться другими
тестами одновременно):

```powershell
docker compose -p pricewatch -f compose.yaml exec -T -e PRICEWATCH_INTEGRATION=1 -e POSTGRES_DB=test_pricewatch web python -m tests.integration.analytics_demo
docker compose -p pricewatch -f compose.yaml --profile integration up -d --wait integration-web
```

На `http://127.0.0.1:8011/accounts/login/` войдите как `stage5_chart_demo` с паролем
`PriceWatch-demo-5!` (только локальная тестовая БД). Откройте Demo One:
выберите 7/30/90/all, наведите на точку, перелистните наблюдения. В списке
выберите два Demo и нажмите «Сравнить выбранные»; легенда скрывает ряды.
Проверьте также пустой товар, весы с одной ценой, неизменный фильтр и длинную
историю. Сравнение USD с RUB должно показать ошибку. Генератор откажется
перезаписывать существующего пользователя; при повторном запуске используйте
уже созданные данные. Он не публикует задания и не обращается по URL.

После проверки остановите только тестовые сервисы:

```powershell
docker compose -p pricewatch -f compose.yaml --profile integration stop integration-web integration-beat integration-worker fixture
```

Перед следующим полным тестированием остановите профиль интеграции. Если
демонстрационные записи остались в переиспользуемой тестовой БД, добавьте
`--create-db` к pytest: это пересоздаст **только test_pricewatch**, не рабочую БД.
Для отладки Python удобно смотреть `response.context['analyses']` в тесте,
SQL — CaptureQueriesContext; в браузере — JSON script `price-chart-data`,
HTTP локальных static-файлов и console. Не правьте сохранённые цены ради графика.

## Ограничения производительности

- Объём Python/HTML/JSON ограничен, однако точный AVG/Min/Max и оконная выборка
  должны обработать историю в PostgreSQL. «Всё время» на миллионах строк
  может требовать дорогих сканирований и сортировок. На этом этапе нет кеша,
  материализованных агрегатов, копии истории и новых индексов. Для реального
  объёма сначала измеряйте EXPLAIN ANALYZE; обычно помогает сужение периода.
- Пагинация использует COUNT и OFFSET. Очень глубокие страницы будут медленнее;
  keyset-пагинация имеет смысл при подтверждённой потребности.
- Выбор сравнения ограничен одной страницей списка и пятью товарами.
- Координаты Chart.js имеют точность JavaScript Number; таблица и вычисления
  сохраняют Decimal. Tooltip выводит исходную строку, но очень близкие большие
  цены могут визуально совпасть.
- В пределах одного HTTP-запроса используются несколько SELECT. Верхняя
  временная граница фиксирована; это не исторический снимок с REPEATABLE READ.
  Одновременное ручное исправление/импорт старых дат потребовало бы отдельного
  решения согласованности. Обычные проверки добавляют текущие наблюдения.
