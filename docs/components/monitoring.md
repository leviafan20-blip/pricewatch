# Этап 3: ручной мониторинг товаров

Документ описывает основу ручных проверок. Начиная с этапа 4 к ней добавлено
расписание: см. `scheduling.md`. Парсер, авторизация и хранение результатов
остаются общими для обоих способов запуска.

## Ответственность компонента

Пользователь сохраняет URL и настройки извлечения, запускает проверку вручную,
а затем просматривает цену, наличие и историю. Веб-процесс не загружает товар:
он фиксирует попытку в PostgreSQL и отправляет её UUID через Redis в Celery.
Worker вызывает прежний `services.inspect_url()` со всеми ограничениями этапа 2.
Расписания, графиков, уведомлений и импорта здесь нет.

## Модели и движение данных

`Monitor` принадлежит одному `owner`. Он содержит пользовательское имя,
URL, словарь настроек `ExtractionConfig`, время создания/изменения и
`archived_at`. Удаление заменено архивированием, чтобы сохранить историю.

`CheckRun` — конкретная попытка с UUID, состоянием, временем постановки,
начала и завершения, кодом/сообщением ошибки. Она хранит собственные копии URL
и настроек. Изменение Monitor не меняет уже поставленное задание. Копии
нельзя менять через обычный `save()`; прикладной код их не обновляет.

`Observation` — только успешный результат: название до 1000 символов,
`DecimalField(30, 10)`, валюта, наличие, источник и пояснения. Точность поля
достаточна для существующего парсера, принимающего до 18 цифр и четырёх
десятичных знаков. Связь один-к-одному с CheckRun запрещает два результата
для одной попытки. Monitor определяется через `check_run.monitor`, без
дублирующей внешней связи, которая могла бы противоречить первой.

Процесс проверки:

1. POST проходит авторизацию, CSRF и выбор Monitor по `owner=request.user`.
2. Короткая транзакция блокирует строку Monitor. Она находит существующую
   активную попытку либо создаёт `queued` с копией настроек.
3. После фиксации транзакции UUID публикуется в Redis. В сообщении нет URL,
   cookies, HTML, настроек пользователя или результата.
4. Worker получает UUID и пытается занять PostgreSQL advisory lock Monitor.
   Конкурентная доставка того же задания пропускается.
5. Короткая транзакция переводит попытку в `running`, выдаёт случайный
   `claim_token` и заканчивается. Затем вызывается `inspect_url()`.
6. При успехе одна транзакция сохраняет Observation и `succeeded`. При ошибке
   записываются только `failed`, безопасный код/сообщение и время завершения.
7. Блокировка снимается в `finally`. Карточка читает результат из PostgreSQL;
   отдельный Celery result backend не нужен.

Строковая блокировка не удерживается во время сети. Advisory lock привязан
к отдельному соединению PostgreSQL и переживает короткие транзакции. Это
намеренное требование к развёртыванию: **PgBouncer в transaction pooling
режиме для worker не подходит**. Текущий Compose соединяется с PostgreSQL напрямую.

Частичный уникальный индекс запрещает две `queued/running` попытки одного
Monitor даже при ошибке прикладного кода. Ограничения БД также проверяют
согласованность состояния, времени и ошибки, неотрицательность цены и наличие
валюты при цене. Удаление Monitor/CheckRun с историей защищено внешними ключами.

## Повторы и восстановление

PostgreSQL и Redis не образуют общую транзакцию. Между фиксацией попытки и
публикацией процесс может завершиться. Вместо отдельной outbox-системы на этом
этапе используется явное восстановление: кнопка «Повторить отправку» публикует
тот же UUID. Завершённая попытка не загружается повторно; Observation не дублируется.

Задания подтверждаются после выполнения (`acks_late`); при гибели дочернего
worker включена повторная доставка. Если попытка осталась `running`, но advisory
lock больше никто не держит, worker может продолжить эту же попытку с новым
токеном. Числового lease с автоматическим истечением для Monitor нет: долгий
живой запрос не должен неожиданно разрешить второй запрос.

Проверки выполняются не более 70 секунд до мягкого ограничения и 80 до жёсткого.
Сетевая часть сохраняет общий предел 45 секунд. Visibility timeout Redis — 300
секунд. Автоматических повторов ошибок магазина нет: пользователь видит ошибку
и запускает новую попытку вручную с соблюдением robots и лимитов домена.

Публикация имеет ограниченные тайм-ауты и отключённые повторы подключения.
Если брокер недоступен, ещё не принятая worker попытка становится
`failed / queue_unavailable`. Уже выполняющийся или успешный результат не
перезаписывается ошибкой подтверждения брокера.

Архив отменяет `queued` и запрещает создание новых попыток. Выполняющаяся
проверка может закончиться и сохранить наблюдение. Архив не стирает историю.

## Страницы и права

- `/monitors/` — активные мониторинги, `?state=archived` — архив.
- `/monitors/new/` — создание; сохранение не запускает сеть.
- `/monitors/<id>/` — последняя известная цена, наличие, состояния и история.
- `/monitors/<id>/edit/` — редактирование активного Monitor.
- `/monitors/<id>/archive/` — GET подтверждение, POST архивирование.
- `/monitors/<id>/check/` — только POST постановка/повторная отправка.

Все выборки ограничены владельцем, включая POST. Чужой объект отвечает 404,
значения `owner`, состояния и результатов из формы не принимаются. Шаблоны
экранируют названия и сообщения ошибок. Полная строка запроса URL не выводится
в видимом адресе ссылки; исходный URL доступен только владельцу в ссылке/настройках.
Загрузка и проверка публичности DNS выполняются повторно в worker; доверия
к сохранённому в БД адресу недостаточно.

Верхняя цена выбирается из последнего наблюдения с ценой, а наличие — из
последнего успешного наблюдения. Поэтому «нет в наличии, цена не опубликована»
не уничтожает известную цену. Даты показаны рядом с данными. При смене URL
карточка поясняет, что старая цена получена для предыдущего адреса.
Обновление состояния выполняется обычной ссылкой, без дополнительного JavaScript.

## Как проверить и отладить

Из корня проекта:

```powershell
docker compose up --build -d --wait
docker compose ps -a
docker compose exec web python manage.py migrate --check
docker compose exec web python -m pytest tests/monitoring --ds=config.settings.test --reuse-db
docker compose exec worker celery -A config inspect ping
docker compose logs --tail=100 worker redis
```

После изменения Python-кода worker нужно перезапустить: Django autoreload
перезапускает только веб-процесс.

```powershell
docker compose restart worker
```

Если задание долго в очереди, сначала проверьте worker, Redis и его очередь.
Затем нажмите «Повторить отправку». Не исправляйте статус вручную через SQL:
это может нарушить согласованность данных. `queued/running` не означает,
что получена новая цена; источником результата остаётся Observation.
Сообщение Celery `Task ... succeeded` означает, что доставка обработана;
бизнес-результат может быть `CheckRun.failed`, если ошибка магазина уже
безопасно записана. Смотрите состояние и код CheckRun, а не только журнал Celery.

`queue_unavailable` относится к брокеру. `worker_timeout` — к пределу выполнения.
`internal_error` — к непредвиденной ошибке приложения или недопустимому результату.
Для неё проверьте тесты, настройки и воспроизведите разбор сохранённой страницы
через `parse_product`. Сырые исключения, HTML и query-параметры не пишутся
в пользовательское сообщение или журнал worker.

Коды `host_not_allowed`, `unsafe_address`, `robots_denied`, `timeout`,
`missing_price`, `ambiguous_offers` и остальные ошибки этапа 2 сохраняются
в CheckRun. Порядок их диагностики описан в `scraping.md`.

## Настоящая интеграция в Docker

Тестовый профиль использует отдельную БД `test_pricewatch`, Redis DB 15,
очередь `pricewatch-integration`, prefork worker с двумя процессами и HTTP
fixture на внутреннем порту 8080. Производственные Django/worker используют
свою БД и Redis DB 0. Тесты не требуют реального магазина.

```powershell
# Сначала создать/обновить сохраняемую тестовую БД стандартными тестами.
docker compose exec web python -m pytest --ds=config.settings.test --reuse-db
docker compose --profile integration up -d --wait fixture integration-worker integration-beat
docker compose exec -e PRICEWATCH_INTEGRATION=1 -e PRICEWATCH_RUN_INTEGRATION=1 -e CELERY_BROKER_URL=redis://redis:6379/15 web python -m pytest tests/integration --ds=config.settings.integration --reuse-db
```

В тестовом worker явно выбран `tests.integration.worker:app`. Только этот
модуль подставляет публичный DNS-ответ для `shop.pricewatch.example` и направляет
проверенный TCP-адрес на HTTP fixture. Настоящие HTTPX/HTTPcore, robots,
ограничения размера, `inspect_url()` и парсер продолжают работать. Производственный
worker не импортирует адаптер; разрешения внутренних адресов в приложении нет.
Без `PRICEWATCH_INTEGRATION=1` настройки/адаптер отказываются запускаться.

Стандартный прогон пропускает интеграционные тесты с явной причиной. Они
запускаются отдельно; Celery eager не используется. Не запускайте два прогона
с одной тестовой БД одновременно. После запуска тестовых сервисов используйте
`--reuse-db`, чтобы не пытаться удалить БД, к которой подключён worker.

Для просмотра изолированного интерфейса:

```powershell
docker compose --profile integration up -d --wait integration-web
docker compose exec integration-web python manage.py createsuperuser
```

Адрес по умолчанию `http://127.0.0.1:8011`. Можно создать обычного тестового
пользователя через admin. Для товара используйте
`http://shop.pricewatch.example/products/0123456789abcdef0123456789abcdef/success`.
Вместо `success` доступны `slow`, `missing`, `error`. Эти адреса обслуживает
только тестовый worker. Профиль использует тестовый SECRET_KEY и быстрый
хешер паролей: он предназначен исключительно для локальной проверки.

Остановить только добавленные тестовые сервисы, сохранив их данные:

```powershell
docker compose --profile integration stop integration-beat integration-web integration-worker fixture
```

## Ограничения

Для реальных URL администратор задаёт точные `SCRAPING_ALLOWED_HOSTS`; по
умолчанию список пуст. CSS-селекторы настраиваются в форме, нестандартные
словари наличия — через Python-сервис; их редактора в интерфейсе пока нет.
Для ручных заданий восстановление остаётся ручным. Плановые задания с этапа 4
восстанавливаются диспетчером с ограничением количества отправок.
В случае сбоя БД записать ошибку сразу невозможно; после восстановления
соединения повторная отправка позволяет продолжить попытку.
Advisory locks предполагают прямые сессии PostgreSQL. Redis хранит очередь
в AOF-volume без eviction; регулярные резервные копии и публичное развёртывание
не входят в этот этап.
